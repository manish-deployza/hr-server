# Auth & Security

> **Note on OWASP version**: this doc maps controls against the OWASP Top 10 **2025** category set as circulated in OWASP's 2025 release cycle, to the best of available knowledge at time of writing. OWASP occasionally adjusts category names/ordering between release candidate and final publication — **before sign-off, confirm the mapping below against the current list at owasp.org**, since a category name changing doesn't change the underlying control, but this doc's headings should match whatever's official.

## Authentication

- **Multi-tenant login**: the request's subdomain resolves the `organization` first (see [multi-tenancy.md](multi-tenancy.md)); `POST /api/auth/login` then looks up the user by `(organization_id, email)`, never by email alone — a login on `acme.yourapp.com` can only ever authenticate an Acme employee, regardless of whether the same email exists at another tenant.
- Login: `POST /api/auth/login` with email + password → JWT access token, now carrying an `organizationId` claim alongside `sub`/`role`/`isManager`. No refresh-token flow for v1 — this is an internal HR tool, not a consumer app; a ~60 minute token lifetime with re-login on expiry is enough.
- **Every authenticated request** re-derives the org from the subdomain and checks it against the JWT's `organizationId` claim — a mismatch is rejected (401) before the request reaches any controller. This is what stops a token leaked/replayed against a different tenant's subdomain from being trusted just because it's a validly-signed token. Add refresh tokens only if session-length complaints show up in practice.
- Passwords: BCrypt (`spring-security-crypto`'s `BCryptPasswordEncoder`), cost factor ≥ 12.
- Accounts are HR-created, not self-service signup — HR sets a temporary password directly on the account. There is no forced-reset-on-first-login flag; `POST /api/auth/change-password` is available any time the user knows their current password (see [multi-tenancy.md](multi-tenancy.md) for the removed `force_password_reset` column and its planned `NULL password_hash` replacement, not yet built).
- Login failure responses are identical whether the email doesn't exist or the password is wrong ("invalid credentials") — no user enumeration via the error message.
- No CAPTCHA/lockout complexity for v1 — add basic rate limiting on `/api/auth/login` (see below) as the first line of defense; add account lockout only if brute-force attempts are actually observed.

## Authorization

Two stored roles on `employee.role`: `EMPLOYEE`, `HR`.

- `HR` → full access, enforced via `@PreAuthorize("hasRole('HR')")` at the controller level for every `/api/hr/**` endpoint.
- `EMPLOYEE` → default. "Manager" capability is **derived**, not a stored role: authorized by checking `targetEmployee.managerId == callingUser.id` in the service layer for every `/api/manager/**` action. Recommendation confirmed from architecture discussion: a stored `is_manager` flag would drift the moment a `manager_id` reassignment happens elsewhere in the system; deriving it from the relationship that already has to be checked anyway removes that whole class of bug.
- JWT claims: `sub` (employee id), `role`, `isManager` (boolean, computed at login time as `EXISTS(SELECT 1 FROM employee WHERE manager_id = :id)` — used only to drive frontend nav, **never** trusted as the actual authorization check, which always re-verifies `managerId` against the specific target employee on every manager action).
- Every write endpoint re-checks ownership/relationship server-side even when the frontend already filtered the list — the frontend hiding a button is UX, not a security boundary.

## OWASP Top 10 (2025) mapping

| # | Category | Where it applies here | Mitigation |
|---|---|---|---|
| 1 | **Broken Access Control** | Manager/HR endpoints, employee self-service scoped to "my own records" — **and, since going multi-tenant, cross-company data isolation** | Every controller method re-verifies ownership/role server-side (see Authorization above), not just via JWT presence. Object-level checks (`leaveRequest.employeeId == callingUser.id` or `== callingUser.managedEmployeeIds`) on every GET/POST that takes an `{id}`, not just on writes — prevents IDOR (e.g. employee A reading employee B's leave request by guessing `/api/leave-requests/57`). Cross-tenant isolation is enforced structurally, not per-query: the Hibernate `@Filter` described in [multi-tenancy.md](multi-tenancy.md) scopes every query to the request's `organization_id` at the ORM session level, so a forgotten `WHERE` clause in a new query can't leak another company's data — plus the JWT-vs-subdomain org cross-check above. |
| 2 | **Security Misconfiguration** | Spring Security filter chain, Tomcat, MySQL, CORS | Explicit `SecurityConfig` (JavaConfig, since this is plain Spring not Boot — no implicit defaults to audit): deny-by-default filter chain, CORS locked to the known React origin only, no verbose Spring stack traces returned to clients in production (`@ControllerAdvice` maps exceptions to generic error bodies), DB user has only the privileges the app needs (no `DROP`/`GRANT`), default MySQL/Tomcat accounts disabled. |
| 3 | **Software Supply Chain Failures** | Every third-party Maven/npm dependency | Pin exact versions in `pom.xml`/`package-lock.json` (no floating ranges), run `mvn dependency:tree` / `npm audit` in CI, subscribe to security advisories for Spring Framework/Hibernate/React — this matters more without Boot's managed BOM, since versions aren't centrally curated for you. |
| 4 | **Cryptographic Failures** | Passwords, JWT signing, data in transit | BCrypt for passwords (never reversible encryption). JWT signed with a strong secret (HS256 minimum, or RS256 if key rotation is wanted) stored in an environment variable/secrets manager, never in source control. TLS everywhere (Tomcat behind a TLS-terminating proxy or with its own cert) — no plaintext HTTP in any environment that touches real employee data (salary, medical/maternity details qualify as sensitive personal data). |
| 5 | **Injection** | Every endpoint accepting user input, especially free-text fields (`reason`, `hr_notes`, `comments`) — **and HR-authored rule expressions** | Parameterized queries throughout — Hibernate/JPA with named/positional parameters, never string-concatenated JPQL or native SQL. `@Valid` bean validation on every DTO. React escapes output by default (no `dangerouslySetInnerHTML` on user-supplied text like `reason`/`comments`), covering the XSS half of injection risk. The rule engine ([rule-engine.md](rule-engine.md)) evaluates HR-authored SpEL expressions using `SimpleEvaluationContext` only — never `StandardEvaluationContext` — which disables method invocation and constructor calls, since a rule expression is close enough to user input that full SpEL would otherwise be a code-execution vector. |
| 6 | **Insecure Design** | The approval-chain bypass path, exit encashment, LOP imposition | These are exactly the flows this design already treats carefully rather than bolting security on after: HR-imposed LOP and dispute overrides are audit-logged by design (see [04](workflow-state-machines.md)), not an afterthought; the approval state machine has no "skip a step" code path — every state transition is validated against the configured chain, so there's no way to reach `APPROVED` without walking every mandatory step (or going through the explicit, logged HR-bypass method). |
| 7 | **Authentication Failures** | Login, session/token handling | Covered under Authentication above: BCrypt, generic failure messages, short-lived JWTs, forced password change on first login. Add basic rate limiting (e.g. a request-count filter or reverse-proxy rule) on `/api/auth/login` — a handful of lines, not a WAF, is enough for an internal tool. |
| 8 | **Software or Data Integrity Failures** | CI/CD pipeline, deployment artifact (WAR) | Build the WAR from CI (not a hand-built local artifact deployed manually), verify dependency checksums, don't deserialize untrusted data (no Java native serialization anywhere in the API — JSON only via Jackson with typing locked down, not polymorphic deserialization from client input). |
| 9 | **Logging & Alerting Failures** | Audit trail, security-relevant events | `audit_log` table (see [02](database-schema.md)) already captures HR overrides, imposed LOP, exit finalization, and leave-type config changes. Extend the same pattern to auth events (failed logins, password changes) at INFO/WARN level in application logs — not necessarily a new table, since these are high-volume/low-value-per-row compared to business-data audit entries; a log aggregator query covers "how many failed logins for user X in the last hour" well enough for v1. |
| 10 | **Mishandling of Exceptional Conditions** | Error paths across the API (validation failures, DB constraint violations, scheduled job failures) | Global `@ControllerAdvice` maps every exception type to a defined error response — no unhandled exception ever returns a raw stack trace or a 500 with internal details to the client. Scheduled jobs (`AccrualJob`, `LopReturnCheckJob`, etc.) wrap their body in try/catch that logs and alerts rather than silently failing — a failed accrual job that nobody notices is worse than a job that throws visibly, since it corrupts the ledger's completeness silently. |

## Data sensitivity notes specific to this domain

- **Maternity/paternity `situation_type` and `reason` fields** carry medical/family information — treat as sensitive personal data even though the schema stores it as plain text. Access to another employee's leave request detail (beyond status/dates visible to a manager for scheduling) should be restricted to the employee themselves and HR — a manager approving a maternity request needs to see enough to approve it, not necessarily the full medical reason; consider whether the manager view truncates `reason` for these leave types (a product decision to confirm with HR, not just an engineering one).
- **`basic_salary`** is only readable via `/api/hr/employees/**` (HR only) and the exit-settlement endpoints — never exposed on any employee-facing or manager-facing endpoint.

## What's deliberately not built for v1

- No SSO/OAuth integration — plain email+password is enough for a single-company internal tool; add SSO if the company already runs one (e.g. Google Workspace) and wants to retire separate passwords.
- No MFA — reasonable for v1 given the sensitivity level (HR data, not financial transactions); revisit if a security review of the finished system recommends it.
- No WAF/API gateway — a reverse proxy (Nginx/Tomcat's own connector) with basic rate limiting covers v1; add a dedicated gateway only if traffic/attack patterns justify it.
